Think Answer:
Does changing the number of blocks change the thread ID (threadIdx.x) values?
-> NO. threadIdx.x is local to each block and always ranges from 0 to (blockDim.x - 1).
   Adding more blocks creates additional block instances (different blockIdx.x),
   but within each block, threadIdx.x restarts from 0.
   To obtain a unique identifier across the whole grid, Global Thread ID must be computed:
   GlobalID = blockIdx.x * blockDim.x + threadIdx.x

Analysis & Answers:
1. Does increasing threads per block always improve performance?
   -> NO. Beyond a certain threshold (e.g. 256 or 512), performance plateaus or can
      even slightly degrade due to register pressure, reduced warp occupancy, and
      limited shared memory per SM.
2. What happens when the number of threads is not an exact multiple of N?
   -> Ceiling division creates an extra block, causing the total thread count to exceed N.
      The 'trailing' threads in the last block have Global IDs >= N.
3. Why is the boundary check necessary?
   -> Without 'if (id < N)', the trailing threads would write to memory addresses
      outside the allocated array bounds, triggering segmentation faults, invalid
      memory access errors (cudaErrorIllegalAddress), or data corruption.

=================================================================
 ANALYSIS & DISCUSSION ANSWERS                                   
=================================================================
1. Which implementation is fastest for smaller input sizes (10^5)?
   -> OpenMP or Sequential CPU is often fastest for small inputs because
      the PCIe data transfer overhead and CUDA runtime launch latency dominate
      the small computational workload.

2. What happens as the input size increases (10^6, 10^7)?
   -> CUDA GPU kernel speedup increases dramatically. The sheer number of
      CUDA cores (over 2000 hardware execution threads) provides massive memory
      bandwidth and computation throughput that easily surpasses CPU cores.

3. Why might CUDA have overhead for small problems?
   -> CUDA kernel launch latency (~5-10 microseconds), thread block scheduling,
      and PCIe memory copying (H2D and D2H) introduce fixed latency costs that
      exceed the tiny compute time of small arrays.

4. What additional overhead is introduced by host-device data transfer?
   -> Host-to-Device and Device-to-Host transfers must traverse the PCIe bus
      (typically 8-16 GB/s), which is orders of magnitude slower than on-chip GPU
      VRAM bandwidth (over 100-200 GB/s).

5. Why can CUDA become advantageous for highly parallel workloads?
   -> For large data parallel workloads, thousands of GPU threads operate in parallel,
      overlapping memory latency via warp scheduling and delivering tens of times
      higher throughput than multi-core CPUs.
